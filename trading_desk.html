What you are looking at

This page is an experimental reference implementation of directly executed machine-learning inference on the GenesisL1 blockchain. Six gradient-boosted decision tree (GBDT) classifiers — three asset pairs of long/short models — are registered with NFTs on chain id 29. Their serialized tree topology, split thresholds, and leaf values are recoverable from public contract bytecode rather than a private inference API. A caller can submit a feature vector to predictView(modelId, packedFeatures) on the ForestRuntime contract.

For a wider context on what this enables and where it's going, see the GL1F protocol pitch deck, the GenesisL1.com chain documentation, and the L1coin.com ecosystem page.

The two innovations that matter

1. Consensus execution

When inference is submitted as a transaction, validating nodes execute the same integer traversal over the same registered bytes and input. An eth_call is instead re-executed by the selected RPC provider and inherits that provider's state and trust assumptions. In both modes, a user can independently replay the public model and input.

2. Public execution provenance

Each registered model is associated with an NFT and public metadata. The deployed registry records a model identifier, storage pointers, selected dimensions, creator address, and registration time. These records support byte- and execution-level replay; they do not by themselves certify the training data, scientific validity, authorship, or absence of registration front-running.

How an inference flows

  1. Feature computation The browser (or off-chain daemon) fetches recent OHLCV candles and funding-rate history from a market-data source, then computes model inputs locally. The current feature builder uses the completed OHLCV values of the evaluated candle, so a prediction must be timestamped after that candle closes and its forecast horizon must begin after the close.
  2. Quantization & packing Each feature is multiplied by scaleQ = 10⁶, rounded to int32, and packed in little-endian byte order in the schema's exact feature order. The result is a flat byte string handed to the contract.
  3. On-chain eth_call The dApp invokes ForestRuntime.predictView(modelId, packedFeatures) as an eth_call. No transaction is mined and no consensus receipt is produced: the selected RPC re-executes the runtime against its chosen block state. Users who need independently attested execution should replay locally or submit the corresponding transaction path.
  4. Sigmoid & presentation The dApp divides the returned logit by scaleQ to recover a real number, applies σ(x) = 1/(1+e−x) to get a probability, and renders it. The same dApp can re-run any past candle (see Blockchain inference tab) or replay the full history (see Predictions history).

GBDTs for tabular data

Gradient-boosted decision trees are a well-established methodology for predictive modeling on tabular data — the kind of data this dApp works with: OHLCV candles, funding rates, derived volatility and momentum features arranged as rows × columns. The model is an ensemble of shallow decision trees built sequentially, each one trained to correct the residual error of the trees that came before. The final prediction is the sum of every tree's contribution, then mapped through the sigmoid to yield a probability.

What makes GBDTs the right tool here:

  • Excellent on heterogeneous numeric features. Returns, volatility ratios, RSI, funding cumulants, hour-of-day, day-of-week — all of these live on different scales and have different relationships to the target. Trees handle this natively: each split is feature-local, so wildly different ranges and units coexist without preprocessing or normalization.
  • Captures non-linear interactions automatically. The model can discover that "high RSI matters more when funding is elevated" without anyone hand-engineering the interaction term. Depth-7 to depth-9 trees explore conjunctions of up to ~7-9 conditions per leaf.
  • Configurable regularization. Tree depth, minimum leaf size, learning rate, and validation-based early stopping constrain the fitted ensemble. These controls reduce capacity but do not guarantee generalization.
  • Per-feature diagnostics. Permutation importance and split-usage statistics (visible in the per-model spec sheets) estimate which features the ensemble relies on. For ZEC upside the leading recorded diagnostics are ATR_ratio100 and close_to_ema5; for ZEC downside they are hour and funding_cum_24h. These diagnostics support inspection but are not causal attributions or complete explanations.
  • Deterministic integer inference. A trained tree is a fixed structure of integer comparisons against integer thresholds. Under the documented canonical-storage, metadata, access-gate, and exact-accumulation premises, the deployed EVM evaluator and a conforming local evaluator return the same integer output. Public model bytes make independent replay practical; an eth_call still inherits the selected RPC provider's chain-state assumptions.
  • Compact and cheap to evaluate. The six models in this dApp range from 1,008 to 2,500 trees with serialized sizes between 2.7 MB and 9.5 MB on-chain. Inference is a tight loop of comparisons; a single predictView call returns in seconds on the GenesisL1 RPC.

The model cards report exploratory metrics from the original deployment. They are not a publication-grade trading result without archived datasets, chronological walk-forward evaluation with purge/embargo, a locked final test period, class-prevalence baselines, calibration and precision–recall analysis, and a pre-registered scoring rule.

What this dApp does NOT do

  • Training is off-chain. Models are trained on historical data using the repository's browser, C++, or Python trainer (open source under the repository's MIT license). What is registered is the resulting frozen ensemble, not a proof of the training procedure or dataset.
  • Market data is off-chain. Candles and funding history come from Binance Futures via the dApp's fetch calls. The chain has no oracle for them. This is a deliberate architecture choice — the on-chain part is the verifiable computation; getting fresh inputs into the EVM is a separate (and well-understood) oracle problem.
  • No order execution. This is a prediction surface, not an automated trading system. Probabilities are emitted; humans (or downstream contracts) act on them. The dApp explicitly does not place trades.

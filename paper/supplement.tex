\section{Scope and notation}
\label{sec:supp-scope}

This supplement provides the byte-level definitions, supporting proofs, and
experimental details for the accompanying article. A model is a complete,
fixed-depth integer tree ensemble whose serialized core can be evaluated
locally or reconstructed from EVM runtime-code chunks. The results concern
representation and execution. They do not establish predictive validity of
the application named in a model's metadata.

The formal results distinguish the serialized byte string, the integer
function it defines, and the registry record used to locate those bytes.
Their equivalence is conditional on canonical parsing, exact reconstruction,
consistent registry fields, identical packed inputs, and exact integer
accumulation. They are handwritten proofs of evaluator specifications.
Finite tests assess the implementations separately; neither the proofs nor
the tests establish a verified compilation from source to deployed bytecode.
Training uses floating-point arithmetic and is therefore covered by an
explicit, finite conformance profile rather than a universal determinism
claim.

\section{Binary layout}
\label{sec:supp-layout}

All multibyte integers are little-endian. Table~\ref{tab:supp-header} records
the fixed header shared by the two supported core versions. The v1 header is
followed immediately by scalar trees. In v2, the fixed header is followed by
$K$ signed int32 base values and then the trees, in output-major order.

\begin{table}[htbp]
\centering
\small
\caption{GL1F fixed header. Offsets and sizes are in bytes.}
\label{tab:supp-header}
\begin{tabularx}{\linewidth}{rrlXX}
\toprule
Offset & Size & Type & v1 scalar & v2 vector\\
\midrule
0  & 4 & Bytes & \texttt{GL1F} & \texttt{GL1F}\\
4  & 1 & uint8 & Version 1 & Version 2\\
5  & 1 & uint8 & Reserved, zero & Reserved, zero\\
6  & 2 & uint16 & Feature count $F$ & Feature count $F$\\
8  & 2 & uint16 & Depth $d$ & Depth $d$\\
10 & 4 & uint32 & Tree count $T$ & Trees per output $R$\\
14 & 4 & int32 & Base $a_0$ & Reserved, zero\\
18 & 4 & uint32 & Scale $s$ & Scale $s$\\
22 & 2 & uint16 & Reserved, zero & Output count $K$\\
\bottomrule
\end{tabularx}
\end{table}

For a complete tree of depth $d$, let $I(d)=2^d-1$ and $L(d)=2^d$.
The internal-node array contains $I(d)$ eight-byte records in breadth-first
heap order. Within each record, the feature index occupies bytes 0--1, the
signed int32 threshold occupies bytes 2--5, and bytes 6--7 are reserved and
zero. The threshold is intentionally unaligned. The internal-node array is
followed by $L(d)$ signed int32 leaf values. A tree therefore occupies
$b(d)=12\cdot2^d-8$ bytes, with no inter-tree padding.

Using zero-based indices, tree $t$ begins at $24+tb(d)$ in v1. Tree $t$ of
output $k$ begins at $24+4K+(kR+t)b(d)$ in v2. Relative to a tree's first
byte, internal node $j$ begins at $8j$ and leaf $u$ begins at $8I(d)+4u$.
These expressions permit bounds checking before decoding. The full grammar,
including the distinction between wire-field limits and the narrower
first-party deployment profile, is maintained in \path{FORMAT_SPEC.md}.

\section{Training conformance and numerical corrections}
\label{sec:supp-training}

The publication suite invokes the production browser worker under Node.js,
compiles the production C++ trainer, invokes the Python command-line trainer,
and compares the serialized core bytes. Its archived matrix contains 25
distinct three-engine training profiles and five auxiliary controls, giving
30 profile executions, together with one standalone IEEE-754 operation-order
witness. The 18 test methods cover regression, binary classification,
multiclass and multilabel objectives; linear and quantile binning; weighting;
stratification; early stopping; fixed-budget refitting; learning-rate
schedules; seed zero; repeatability; v1/v2 inference; rounding boundaries;
packaging; and malformed-stream rejection. Profiles and test methods are
different counting units.

The tested Linux environment used Python 3.12.13, NumPy 2.3.5, Node.js
24.19.0, and g++ 13.3.0 with C++17, \texttt{-ffp-contract=off}, and
\texttt{-fno-fast-math}. Equality depends on the stated preprocessing,
operation order, feature and class order, random-number consumption, and
compiler settings. No evidence here establishes equality for every input,
platform, compiler, or mathematical library.

\subsection{Histogram arithmetic}

A finite arithmetic witness distinguished multiplying by a cached reciprocal
from dividing by the range before multiplication in linear histogram binning.
These expressions are equivalent over the reals but need not produce the
same binary64 result at a bin boundary. The browser implementation was
changed to use the same divide-then-multiply order as Python and C++. The
witness is retained separately from the training-profile count.

\subsection{Multiclass probability computation}

A generated 4,000-row, 12-feature, four-class profile exposed a second
operation-order discrepancy. Python accumulated the softmax denominator from
binary32-rounded exponentials, whereas JavaScript and C++ accumulated
binary64 exponentials. One byte of the 22,120-byte Python core differed,
representing a one-unit change in a quantized leaf. The corrected profile
uses binary64 exponentials, an ascending-class-index binary64 denominator
sum, a binary32 numerator, binary64 division, and a binary32 result.
All three engines emit a core with SHA-256 digest
\begin{center}
\small\nolinkurl{58e3d9e63c5dd1313872e0c5a07c229b071272f1137f393a0384601329a432eb}
\end{center}
for that fixture. This is a regression result for a specified computation.

\subsection{Rounding and input boundaries}

For a finite binary64 argument $z$, the Python and C++ rounding helpers match
JavaScript's \texttt{Math.round} integer result before int32 saturation,
including its half-toward-positive-infinity convention. Directly evaluating
\texttt{floor(z + 0.5)} in binary64 introduces an additional rounding step:
for $z=0.49999999999999994$, that expression returns one whereas
\texttt{Math.round(z)} returns zero. The corrected helpers compare
$z-\lfloor z\rfloor$ with $0.5$ and enforce the relevant integer bounds.
The exact-real definition in Equation~\ref{eq:quantizer} remains a
mathematical abstraction; the preceding product-rounding correction still
applies to production preprocessing.

The browser form preserves seed zero, and the strict Python GL1X loader
rejects nonstandard JSON constants such as \texttt{NaN} and
\texttt{Infinity}. These corrections align the tested input boundaries; they
do not extend the determinism claim beyond the documented finite-input
profile. The inference specification and deployed contracts were unchanged.

\section{Experimental methods and additional results}
\label{sec:supp-experiments}

\subsection{End-to-end trainer timing}
\label{sec:supp-timing}

Each timing run used 3,000 rows, 12 features, and 60 depth-4 trees. For each
engine and task, one warm-up preceded 30 measured repetitions. The measured
interval included process startup, parsing, training, serialization, and
output writing. Python and C++ read the same CSV input; JavaScript read an
equivalent JSON numeric matrix, so these timings are not a pure training-kernel
comparison. Engine order was rotated between repetitions. The trainer code
was single-threaded, and host scheduling was not pinned. The host reported
an AMD EPYC 9V74 processor with nine
logical CPUs visible to the execution environment; the measurements do not
characterize the performance of the entire physical server.

All three engines produced byte-identical 11,064-byte cores within each

\subsection{Isolated EVM integration}
\label{sec:supp-integration}

The integration test compiles the unmodified contracts using Solidity
0.8.20, optimizer 200, \texttt{viaIR=true}, and the Istanbul EVM target.
It deploys ModelStore, ModelRegistry, ModelNFT, and ForestRuntime to an
isolated Ganache 7.9.2 chain. Minimal canonical v1 and v2 cores are stored in
17-byte GL1C chunks and pointer tables, reconstructed, and checked against
their content identifiers. An independent bigint reference evaluator is
compared with scalar, vector, and class contract results on six vectors
covering threshold equality and integer extremes. These are local test
transactions and read calls.

\label{sec:supp-scaling}

A complementary local benchmark publishes six deterministic two-feature v1

each shape. All 72 reference/runtime comparisons matched. Gas estimates
refer to the same recorded Solidity/Ganache profile as above.

For the tested scalar decoder, model-code reads within the tree bodies
comprise one feature read and one threshold read per visited node, plus one
leaf read per tree. Their count is $R_{\mathrm{tree}}=T(2d+1)$, excluding
registry, header, and pointer-resolution accesses. A descriptive
ordinary-least-squares fit to the six unrounded means was
\[
\widehat{\mathrm{gas}}\approx42{,}900+1{,}708.3R_{\mathrm{tree}},
\]
with $R^2\approx0.99998$ and maximum absolute relative residual 1.45\%.
This six-point fit describes the tested shapes; it is not a gas bound or a
forecast of live-network fees. Raw observations and unrounded statistics are
stored in \path{benchmarks/results/evm_scaling_benchmark.json}.

\section{Historical deployment observation}
\label{sec:supp-historical}

The repository retains factual summaries of a provider-attested observation
at GenesisL1 block 13,342,043, with recorded hash
\nolinkurl{0xffd825db1bb2534052a604db9584d361111d8bc9e19d753b0ee3861bf320d1b9},
in \path{benchmarks/results/LIVE_CHAIN_WITNESS.md} and
\path{benchmarks/results/LIVE_CHAIN_WITNESS_EXTENDED_V2.md}. Those summaries
report reconstruction of 31,185,324 bytes across 12 active models and
matching local/provider-returned integer outputs. The raw provider responses
and reconstructed bytes for that historical observation were not retained
in the repository. Consequently, it cannot be replayed offline and is not
used as the principal reproducibility evidence for this article. The model
names in those records identify registered artifacts; they do not establish
the accuracy of the named prediction tasks.

\section{Reproduction}
\label{sec:supp-reproduction}

The repository's \path{REPRODUCIBILITY.md} specifies the environment,
installation procedure, individual evidence commands, and archived result
files. After installing those dependencies, the following commands run the
local verification suite and regenerate the timing and scalar-scaling
records:

\begin{verbatim}
make verify
python3 benchmarks/publication_benchmark.py \
  --rows 3000 --features 12 --trees 60 --repeats 30 \
  --out benchmarks/results/publication_benchmark.json
npm run benchmark:evm
\end{verbatim}

These commands use local processes and an isolated EVM. They do not submit
transactions to GenesisL1. The checked-in parity and local integration
records include source-input SHA-256 digests; the verification suite checks
those digests and the numerical invariants used in the article. A fresh
network observation requires separate read-only RPC access and must be
identified by its own block and retained responses. Provider-returned state
is distinct from an independently verified proof of chain consensus or
finality.
